# 11. Type erasure как шаблон проектирования

## Суть

Type erasure скрывает конкретный тип объекта за единым набором операций.

Пользователь обёртки знает:

- какие операции доступны;
- кому принадлежит объект;
- можно ли копировать обёртку.

Но не зависит от фактического типа объекта.

```cpp
std::function<int(int)> function = SomeFunctor{};
```

Снаружи известна только сигнатура `int(int)`, а тип `SomeFunctor` стёрт.

## Когда нужен type erasure

- разные несвязанные типы должны храниться в одном контейнере;
- конкретная реализация выбирается во время выполнения;
- нужен стабильный нетемплейтный интерфейс;
- хочется уменьшить связанность модулей;
- важен набор операций, а не иерархия исходных классов.

Типы не обязаны наследоваться от общего класса. Требования проверяются в момент создания обёртки.

## Основные компоненты

Классическая реализация содержит:

1. внутренний интерфейс с доступными операциями;
2. шаблонную модель для конкретного типа;
3. внешнюю нетемплейтную обёртку;
4. механизм владения, копирования и уничтожения.

```text
Drawable
  └── unique_ptr<Concept>
          ├── Model<Circle>
          ├── Model<Button>
          └── Model<CustomType>
```

Исходные `Circle`, `Button` и `CustomType` не знают о `Concept` и не связаны наследованием.

## Реализация через Concept/Model

```cpp
#include <memory>
#include <utility>

class Drawable {
private:
    struct Concept {
        virtual void Draw() const = 0;
        virtual std::unique_ptr<Concept> Clone() const = 0;
        virtual ~Concept() = default;
    };

    template <typename T>
    struct Model final : Concept {
        explicit Model(T value)
            : value_(std::move(value)) {}

        void Draw() const override {
            value_.Draw();
        }

        std::unique_ptr<Concept> Clone() const override {
            return std::make_unique<Model>(*this);
        }

        T value_;
    };

public:
    template <typename T>
    Drawable(T value)
        : object_(std::make_unique<Model<T>>(std::move(value))) {}

    Drawable(const Drawable& other)
        : object_(other.object_->Clone()) {}

    Drawable& operator=(const Drawable& other) {
        Drawable copy{other};
        object_.swap(copy.object_);
        return *this;
    }

    Drawable(Drawable&&) noexcept = default;
    Drawable& operator=(Drawable&&) noexcept = default;

    void Draw() const {
        object_->Draw();
    }

private:
    std::unique_ptr<Concept> object_;
};
```

Любой копируемый тип с подходящим методом `Draw() const` можно сохранить в `Drawable`.

## Пример с разными контейнерами

```cpp
struct VectorCollection {
    std::vector<int> values;

    void Add(int value) {
        values.push_back(value);
    }
};

struct ListCollection {
    std::list<int> values;

    void Add(int value) {
        values.push_back(value);
    }
};
```

Type-erased обёртка может предоставить общий `Add(int)` без изменения исходных классов и без общего базового типа.

## Возможные реализации

Type erasure не требует именно виртуальных функций. Используются разные техники:

- внутренние `Concept/Model` с виртуальным интерфейсом;
- таблица указателей на операции;
- function pointers и `void*` внутри безопасной обёртки;
- small-object optimization;
- owning и non-owning представления.

Интерфейс важнее конкретного внутреннего механизма.

## Стандартные примеры

| Тип | Что стирается | Владение | Доступные операции |
|---|---|---:|---|
| `std::function<R(Args...)>` | Тип callable | Да | Вызов, копирование |
| `std::move_only_function<R(Args...)>` | Тип callable | Да | Вызов, перемещение |
| `std::function_ref<R(Args...)>` | Тип callable | Нет | Вызов |
| `std::any` | Тип хранимого значения | Да | Проверка типа, `any_cast` |
| `std::shared_ptr<T>` | Тип deleter/allocator в control block | Да | Уничтожение ресурса |

### Важное отличие умных указателей

У `std::shared_ptr<T>` тип deleter не входит в тип самого `shared_ptr` и стирается в control block:

```cpp
std::shared_ptr<Resource> resource(
    new Resource,
    CustomDeleter{}
);
```

У `std::unique_ptr<T, Deleter>` deleter — шаблонный параметр и часть типа:

```cpp
std::unique_ptr<Resource, CustomDeleter> resource;
```

Поэтому обычный `unique_ptr` с пользовательским deleter не является примером стирания его типа.

## Сравнение подходов

| Подход | Набор типов | Операции | Выбор реализации | Основная цена |
|---|---|---|---|---|
| Шаблон | Открытый | Заданы выражениями/concepts | Compile time | Инстанциации, связанность заголовков |
| Виртуальный интерфейс | Открытый через наследование | Заданы базовым классом | Runtime | Иерархия, косвенный вызов |
| Type erasure | Открытый без наследования исходных типов | Заданы обёрткой | Runtime | Косвенный вызов, возможная аллокация |
| `std::variant` | Закрытый | Внешние посетители | Runtime по индексу | Фиксированный список альтернатив |
| `void*` | Неограниченный | Не описаны типом | Вручную | Нет типобезопасности и управления жизнью |

## `void*`

`void*` хранит адрес объекта неизвестного типа:

```cpp
int value = 42;
void* pointer = &value;

int restored = *static_cast<int*>(pointer);
```

Без дополнительного контракта неизвестны:

- фактический тип;
- размер объекта;
- разрешённые операции;
- способ уничтожения;
- владеет ли указатель объектом;
- срок жизни объекта.

Неправильное приведение и последующее чтение приводит к UB.

```cpp
double value = 3.14;
void* pointer = &value;

// UB: фактический объект не является int.
// int result = *static_cast<int*>(pointer);
```

Разыменовать `void*` напрямую нельзя. Стандартная арифметика указателей над `void*` также запрещена, потому что размер элемента неизвестен.

## Почему безопасная обёртка лучше `void*`

Type-erased обёртка связывает данные и таблицу допустимых операций:

```text
object storage + invoke + copy/move + destroy
```

Это позволяет:

- проверить совместимость типа при создании;
- автоматически уничтожить правильный объект;
- запретить недоступные операции;
- выразить владение в самом интерфейсе;
- сохранить RAII.

Внутри реализации может использоваться `void*`, но он не выходит в пользовательский API без сопровождающей типовой информации.

## Copyable и move-only обёртки

Операция `Clone()` требует копируемости исходного объекта. Если обёртка должна поддерживать move-only типы, копирование удаляют:

```cpp
Drawable(const Drawable&) = delete;
Drawable& operator=(const Drawable&) = delete;
Drawable(Drawable&&) noexcept = default;
```

Набор специальных методов внешней обёртки является частью её контракта.

## Подводные камни

### 1. Не забывайте виртуальный деструктор внутреннего интерфейса

Удаление `Model<T>` через указатель на `Concept` без виртуального деструктора приводит к UB.

### 2. Копирование требует clone

Поверхностное копирование владеющего указателя либо невозможно, либо создаёт двойное владение. Нужна полиморфная копия либо move-only интерфейс.

### 3. Универсальный конструктор может перехватить саму обёртку

Шаблонный конструктор стоит ограничить, исключив `Drawable` и проверив требуемые операции через concept.

### 4. Type erasure не гарантирует аллокацию

Простая реализация с `unique_ptr` аллоцирует, но SBO может хранить небольшой объект внутри обёртки.

### 5. Type erasure не гарантирует виртуальные вызовы

Таблица свободных функций позволяет реализовать ту же идею без виртуальной иерархии.

### 6. Невладеющая обёртка требует контроля времени жизни

Если внутри хранится указатель на внешний объект, уничтожение исходного объекта оставляет висячую обёртку.

### 7. `memcpy` подходит не для всех C++-объектов

Обобщённый `swap(void*, void*, size)` безопасен только при корректных ограничениях на представление и время жизни. Для обычного C++ используйте типизированный `std::swap`.

### 8. Стирается тип, но не контракт

Чем меньше операций предоставляет обёртка, тем проще обеспечить корректность, эффективность и стабильность интерфейса.

## Саммари

- Type erasure скрывает конкретный тип за фиксированным набором операций.
- Исходные типы не обязаны иметь общий базовый класс.
- Классическая схема: внутренний интерфейс, `Model<T>` и внешняя обёртка.
- Реализация может использовать virtual, таблицу функций и SBO.
- Copyable-обёртке нужен `clone`; move-only обёртке он не нужен.
- `void*` сам по себе не хранит контракт, тип и правила времени жизни.
- `shared_ptr` стирает тип deleter, а у `unique_ptr` deleter остаётся частью типа.
