# 13. Подходы к обработке ошибок и `std::expected`

## Суть

Способ обработки ошибки должен отражать её семантику:

- отсутствие результата нормально — `std::optional<T>`;
- ожидаемая ошибка должна быть обработана — `std::expected<T, E>`;
- ошибка нарушает обычный ход выполнения и обрабатывается выше — исключение;
- взаимодействие с C API — код ошибки с RAII-обёрткой на границе.

`std::expected<T, E>` появился в C++23 и хранит либо значение `T`, либо ошибку `E`.

## Коды возврата

Классический C-интерфейс возвращает статус, а значение записывает через указатель:

```cpp
int Divide(double lhs, double rhs, double* result);
```

Недостатки:

- результат создаётся до вызова и затем изменяется (Initialize Then Modify);
- статус легко забыть проверить;
- владение и допустимость указателя не выражены;
- значение и ошибка передаются разными каналами;
- RAII-объекты неудобно создавать напрямую.

Коды возврата не исчезли: они необходимы в C API, системных интерфейсах и некоторых проектах без исключений. В C++ их лучше преобразовывать в более выразительный тип на границе API.

## Исключения

```cpp
double Divide(double lhs, double rhs) {
    if (rhs == 0.0) {
        throw std::invalid_argument{"division by zero"};
    }
    return lhs / rhs;
}
```

Исключения отделяют успешный путь от обработки ошибки и автоматически раскручивают стек, вызывая деструкторы RAII-объектов.

Важно: целочисленное деление на ноль — UB. Для floating-point результат зависит от реализации и поддержки IEC 60559; часто получается бесконечность или NaN. Проверка выше задаёт собственный контракт функции.

Исключения подходят, когда:

- ошибка не является частым обычным результатом;
- текущий уровень не может её обработать;
- проект разрешает исключения;
- важна передача ошибки через несколько уровней вызовов.

Цена зависит от ABI и реализации: успешный путь часто дешёвый, но выбрасывание исключения и размер служебных данных могут быть существенными.

## `pair` и именованная структура

```cpp
struct ParseResult {
    Person value;
    ParseError error;
    bool success;
};
```

Говорящие поля лучше `first` и `second`, но обычная структура может представлять некорректные сочетания:

- `success == true`, но заполнена ошибка;
- `success == false`, но используется значение;
- одновременно конструируются и `value`, и `error`.

Такой результат уместен, когда поля действительно существуют одновременно. Для взаимоисключающих состояний нужен тип-сумма.

## `std::optional`

```cpp
std::optional<Person> ParsePerson(std::string_view input);
```

`optional` хорошо выражает «значение может отсутствовать», но не хранит причину.

Он не заставляет проверять результат автоматически:

- `value()` на пустом объекте бросает `std::bad_optional_access`;
- `operator*` и `operator->` требуют выполненной проверки;
- весь возвращаемый объект можно проигнорировать.

Добавляйте `[[nodiscard]]`, если результат нельзя безопасно пропускать.

## `std::variant<Value, Error>`

```cpp
using ParseResult = std::variant<Person, ParseError>;
```

`variant` хранит только одну альтернативу и не допускает комбинацию «значение и ошибка одновременно». Но его интерфейс общий для произвольных типов-сумм:

```cpp
if (auto* person = std::get_if<Person>(&result)) {
    Use(*person);
} else {
    Handle(std::get<ParseError>(result));
}
```

Для устойчивого паттерна «значение или ошибка» `expected` выражает намерение точнее.

## `std::expected<T, E>`

```cpp
#include <expected>

enum class ParseError {
    EmptyInput,
    InvalidFormat
};

std::expected<Person, ParseError>
ParsePerson(std::string_view input) {
    if (input.empty()) {
        return std::unexpected{ParseError::EmptyInput};
    }

    return Person{"John", 25};
}
```

Чтение результата:

```cpp
auto result = ParsePerson(text);

if (result) {
    Use(*result);
} else {
    Handle(result.error());
}
```

Основной интерфейс:

| Операция | Назначение |
|---|---|
| `has_value()` / `operator bool` | Проверить успешный результат |
| `value()` | Получить значение с проверкой |
| `operator*`, `operator->` | Получить заранее проверенное значение |
| `error()` | Получить ошибку после проверки неуспеха |
| `value_or(default)` | Получить значение либо запасной вариант |

`value()` при ошибке бросает `std::bad_expected_access<E>`. Доступ через `*`, `->` или `error()` требует соответствующего активного состояния.

## `std::unexpected`

Ошибка создаётся явно:

```cpp
return std::unexpected{ParseError::InvalidFormat};
```

`std::unexpected<E>` — класс-обёртка, а не функция. Он отделяет ошибку от значения, даже если `T` и `E` конструируются из похожих аргументов.

```cpp
using Result = std::expected<std::string, std::string>;

Result Read(bool ok) {
    if (!ok) {
        return std::unexpected{std::string{"read error"}};
    }
    return std::string{"content"};
}
```

## Конструирование на месте

```cpp
return std::expected<Person, ParseError>{
    std::in_place,
    "John",
    25
};
```

Ошибка на месте:

```cpp
return std::expected<Person, Error>{
    std::unexpect,
    ErrorCode::Invalid,
    "bad input"
};
```

Теги `std::in_place` и `std::unexpect` позволяют создать активный объект непосредственно внутри `expected`. Используйте их, когда это упрощает работу с некопируемым типом или измерения показывают значимую стоимость перемещения.

## `expected<void, E>`

Операция без полезного значения тоже может вернуть типизированную ошибку:

```cpp
std::expected<void, SaveError> Save(const Document& document) {
    if (!CanWrite()) {
        return std::unexpected{SaveError::ReadOnly};
    }

    Write(document);
    return {};
}
```

Успешное состояние здесь не содержит `void`-объект — только признак успеха.

## Сравнение подходов

| Подход | Причина ошибки | Значение и ошибка взаимоисключающие | Ошибку легко передать выше | Типичный сценарий |
|---|---:|---:|---:|---|
| Код возврата | Да | Зависит от API | Вручную | C API, системный код |
| Исключение | Да | Да | Да, через stack unwinding | Редкий нештатный путь |
| `optional<T>` | Нет | Да | Через проверки | Нормальное отсутствие |
| `variant<T, E>` | Да | Да | Вручную | Общий тип-сумма |
| `expected<T, E>` | Да | Да | Через return/монадический API | Ожидаемая восстанавливаемая ошибка |

## Несколько успешных типов

Возможны два дизайна:

```cpp
std::expected<std::variant<Type1, Type2>, Error> Parse();
std::variant<Type1, Type2, Error> Parse();
```

`expected<variant<...>, E>` сохраняет отдельный канал ошибки и лучше компонуется с операциями `expected`. Плоский `variant` короче для одного посещения, но смешивает ошибки и успешные варианты. Выбор зависит от дальнейшей обработки.

## Подводные камни

### 1. `expected` тоже можно проигнорировать

Помечайте важные функции `[[nodiscard]]` и договоритесь о политике обработки ошибок.

### 2. Не используйте исключение как единственную альтернативу ожидаемой ошибке

Ошибки ввода, валидации и отсутствующие файлы часто являются обычной частью сценария и хорошо выражаются через `expected`.

### 3. Не превращайте каждую исключительную ситуацию в `expected`

Ошибку выделения памяти или нарушение внутреннего инварианта не всегда возможно осмысленно обработать на каждом уровне.

### 4. Ошибка должна содержать контекст

Один `enum` часто недостаточен. Полезный `E` может хранить код, путь, позицию и диагностическое сообщение.

### 5. Не вызывайте `error()` при успехе

Сначала проверяйте `!result`. Аналогично `*result` допустим только в успешном состоянии.

### 6. `expected` не хранит оба объекта одновременно

Размер ориентируется на большую из альтернатив плюс служебные данные и выравнивание, но точный размер зависит от типов и реализации.

### 7. `in_place` не нужен по умолчанию

Простой `return Value{...};` обычно читается лучше. Убирайте перемещение только при реальной необходимости.

### 8. Согласуйте ошибки на границах слоёв

Низкоуровневую ошибку чтения файла часто нужно преобразовать в ошибку конфигурации с дополнительным контекстом.

## Саммари

- Код возврата остаётся важен на границах C API, но в C++ его удобно оборачивать.
- Исключения подходят для ошибок, которые нельзя обработать локально и которые не являются частым результатом.
- `optional` сообщает только об отсутствии значения.
- `variant<T, E>` выражает сумму, но не семантику результата.
- `expected<T, E>` явно хранит либо значение, либо ошибку.
- Ошибка создаётся через `std::unexpected` или `std::unexpect`.
- `expected<void, E>` описывает операцию без возвращаемого значения.
- Выбор механизма зависит от частоты, смысла и места обработки ошибки.
