# 14. Программирование без блокировок и без ожиданий

## Суть

| Подход | Гарантия продвижения |
| --- | --- |
| Blocking | Операция может ждать действий конкретного другого потока, например освобождения мьютекса |
| Lock-free | При продолжающемся выполнении система в целом продвигается; отдельная операция может не завершаться из-за конкуренции |
| Wait-free | Каждая операция завершается за ограниченное число собственных шагов независимо от действий других потоков |

Wait-free — более сильная гарантия, чем lock-free. Ни одна из них сама по себе не гарантирует минимальную задержку по часам или максимальную производительность: поток может быть вытеснен ОС.

Мьютексы проще для защиты сложных инвариантов. CAS позволяет строить неблокирующие алгоритмы, но наличие атомиков или отсутствие явного мьютекса ещё не доказывает гарантию продвижения.

## Примеры

### CAS-цикл: удвоение счётчика

```cpp
#include <atomic>
#include <cstddef>

std::atomic<std::size_t> count{1};

void Double() {
    auto expected = count.load(std::memory_order_relaxed);
    while (!count.compare_exchange_strong(
        expected, expected * 2,
        std::memory_order_relaxed, std::memory_order_relaxed)) {
        // expected обновлён; на следующей попытке результат вычисляется заново
    }
}
```

Для этого целочисленного CAS неудача означает несовпадение: другой поток изменил значение. При lock-free атомарных операциях такой цикл обеспечивает общий прогресс, но конкретный поток может проигрывать снова и снова. Беззнаковое переполнение определено, однако его смысл должен подходить задаче.

### Стек на CAS с безопасным владением узлами (C++20)

Это учебный потокобезопасный стек: он использует атомарный `shared_ptr`, поэтому **не имеет гарантии lock-free**.

```cpp
#include <atomic>
#include <memory>

template <typename T>
class ConcurrentStack {
    struct Node {
        std::shared_ptr<T> data;
        std::shared_ptr<Node> next;

        explicit Node(const T& value)
            : data(std::make_shared<T>(value)) {}
    };

    std::atomic<std::shared_ptr<Node>> head_{nullptr};

public:
    void Push(const T& value) {
        auto node = std::make_shared<Node>(value);
        auto expected = head_.load();
        do {
            node->next = expected;
        } while (!head_.compare_exchange_weak(expected, node));
    }

    std::shared_ptr<T> Pop() {
        auto expected = head_.load();
        while (expected) {
            auto next = expected->next;
            if (head_.compare_exchange_weak(expected, next)) {
                return expected->data;
            }
        }
        return {}; // стек пуст в момент наблюдения
    }

    ~ConcurrentStack() {
        while (Pop()) {}
    }
};
```

Узел полностью создаётся до публикации. После успешного `Push` поля узла больше не меняются, поэтому `next` — обычный `shared_ptr`. Читатели удерживают узлы живыми локальными копиями; `Pop` не обнуляет ссылки в уже опубликованных узлах.

Успешный CAS — точка линеаризации вставки или извлечения: операция выглядит как произошедшая целиком в этот момент. Возврат пустого результата соответствует наблюдению пустой головы. Все операции здесь используют `seq_cst`, чтобы отдельно не усложнять разбор порядков памяти.

## Подводные камни

- `is_lock_free()` не проверяет wait-free. Даже одиночный `fetch_add()` нельзя автоматически объявить wait-free на любой реализации C++.
- Спинлок остаётся блокирующим алгоритмом: остановившийся владелец может остановить остальных. Важны зависимости продвижения, а не наличие системного сна.
- Доказанная lock-free гарантия исключает общий тупик или livelock внутри рассматриваемого алгоритма, но не голодание отдельного потока и не зависания внешнего кода.
- Неудача `compare_exchange_weak` может быть ложной. Объяснение «каждая неудача означает успех другого потока» напрямую применимо не к каждой weak-попытке.
- Аллокатор, деструктор, пользовательский код и `atomic<shared_ptr>` могут использовать блокировки. Нужно анализировать всю операцию, а не только CAS-цикл.
- На сырых указателях нельзя сразу удалять извлечённый узел: другой поток ещё может читать `old_head->next`. Для настоящих неблокирующих структур нужны отдельные способы безопасного освобождения, например hazard pointers или epochs.
- Повторное использование адреса может вызвать **ABA**: CAS видит прежний адрес, хотя узел уже другой. В примере локальное владение удерживает старый узел живым; извлечённые узлы повторно не вставляются.
- `empty()` и `size()` могут быть полезными снимками, но не гарантируют успех последующего `Pop()`. Проверку пустоты и извлечение объединяй в одну операцию.
- Атомарное увеличение индекса буфера ещё не публикует готовый элемент: другой поток может обратиться к слоту до завершения его конструирования.
- Задержавшийся читатель, удерживающий старый узел с неизменяемым `next`, может удерживать целую уже извлечённую цепочку. Её позднее освобождение способно вызвать глубокую цепочку деструкторов; учебный вариант не ограничивает эту задержку освобождения памяти.
- Уничтожать стек можно только после завершения всех обращений к нему. Владение узлами не продлевает жизнь самого стека.
- Конкуренция за кеш-линии и повторные CAS могут сделать такой код медленнее мьютекса. Неблокирующая реализация не является автоматической оптимизацией.

## Саммари

Lock-free гарантирует общий прогресс, wait-free — ограниченное число шагов каждой операции. CAS помогает атомарно менять состояние, но безопасность памяти и гарантии всего алгоритма нужно доказывать отдельно. `shared_ptr` упрощает владение, не обещая отсутствия внутренних блокировок.
