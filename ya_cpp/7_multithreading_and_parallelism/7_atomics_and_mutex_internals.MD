# 7. Атомарность и устройство `std::mutex`

## Суть

- Мьютекс должен **неделимо проверить и занять** свободный ресурс. Отдельные проверка флага и запись не обеспечивают взаимного исключения.
- Атомарная операция не имеет наблюдаемого промежуточного состояния для других обращений к тому же атомарному объекту.
- `std::atomic<T>::exchange(value)` — операция read-modify-write: записывает новое значение и возвращает старое как единое действие.
- Типичный мьютекс имеет быстрый путь захвата через атомарные операции; при конкуренции может немного покрутиться и затем использовать средства ОС для ожидания. Конкретное устройство `std::mutex` стандарт не задаёт.
- **Спинлок** ждёт в активном цикле. Он обеспечивает взаимное исключение, но расходует CPU и не гарантирует быстрое получение блокировки.

## Примеры

### Почему отдельные проверка и запись не работают

```cpp
std::atomic<bool> locked{false};

// Ошибка логики, хотя обращения к самому флагу атомарны:
while (locked.load()) {}
locked.store(true);
```

Два потока могут прочитать `false` до любой записи и оба решить, что получили блокировку. С обычным `bool` здесь дополнительно возникает data race; `volatile` это не исправляет.

### Учебный спинлок через `exchange`

```cpp
#include <atomic>
#include <mutex>

class Spinlock {
    std::atomic<bool> locked_{false};

public:
    void lock() noexcept {
        while (locked_.exchange(true)) {
            // активное ожидание
        }
    }

    void unlock() noexcept {
        locked_.store(false);
    }
};

Spinlock lock;
int value = 0;

void Increment() {
    std::lock_guard guard(lock);
    ++value;
}
```

Только поток, получивший из `exchange(true)` значение `false`, захватил блокировку. Остальные повторяют попытки до освобождения. Все обращения к `value` должны соблюдать этот протокол.

Здесь используется порядок памяти по умолчанию — `seq_cst`. Для такой блокировки достаточно `exchange(true, std::memory_order_acquire)` и `store(false, std::memory_order_release)`: освобождение публикует изменения, следующий успешный захват позволяет их увидеть. Подробности порядков памяти — в следующих уроках.

### Не выпускать данные из-под защиты по ссылке

```cpp
#include <map>
#include <mutex>

template <typename Key, typename Value>
class ThreadSafeMap {
    std::mutex mutex_;
    std::map<Key, Value> data_;

public:
    void Insert(const Key& key, const Value& value) {
        std::lock_guard guard(mutex_);
        data_.insert_or_assign(key, value);
    }

    Value Get(const Key& key) {
        std::lock_guard guard(mutex_);
        return data_.at(key); // копия; отсутствующий ключ вызывает исключение
    }
};
```

Возврат `Value&` оставил бы вызывающему доступ к элементу после освобождения мьютекса. Возврат копии решает это для значений с независимыми данными; указатели внутри копии сами по себе не защищают общие объекты.

## Подводные камни

- Атомарность отдельной операции не делает атомарной последовательность действий или всю структуру данных.
- `std::atomic<T>` не всегда реализован одной инструкцией и не всегда lock-free. `std::atomic_flag` гарантированно lock-free; для него захват делают через `test_and_set()`, освобождение — через `clear()`.
- Спинлок на lock-free атомиках сам **не является lock-free алгоритмом**: остановившийся владелец блокирует продвижение остальных.
- Если владелец вытеснен ОС, остальные могут долго расходовать CPU впустую. Долгие операции, ввод-вывод и выделение памяти под спинлоком особенно нежелательны.
- Частые `exchange()` усиливают конкуренцию за линию кеша. `yield()` — лишь подсказка планировщику, а не гарантия сна, справедливости или прогресса.
- Повторный захват такого спинлока владельцем приводит к бесконечному ожиданию. Освобождать его должен только владелец.
- **Livelock**: потоки постоянно захватывают первые блокировки, не получают вторые, отпускают первые и повторяют цикл без прогресса. Это возможный сценарий, а не неизбежное свойство спинлоков.
- Для нескольких блокировок придерживайся общего порядка; для стандартных мьютексов используй `scoped_lock`. Случайные задержки могут уменьшить столкновения, но сами по себе не доказывают отсутствие livelock.
- Для обычного прикладного кода начинай с `std::mutex`. Выгоду спинлока для очень коротких критических секций нужно подтверждать измерениями.

## Саммари

Взаимное исключение требует атомарного захвата и корректной синхронизации памяти. `exchange` объединяет проверку и запись; спинлок ждёт активно, а типичный мьютекс умеет передать ожидание ОС. Отсутствие гонки данных ещё не гарантирует продвижения программы.
