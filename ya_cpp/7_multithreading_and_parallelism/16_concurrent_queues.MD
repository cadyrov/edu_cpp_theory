# 16. Многопоточные очереди

## Суть

- Производители добавляют задачи, потребители извлекают и обрабатывают их. Проверка наличия элемента и извлечение должны быть одной защищённой операцией.
- **Bounded** ограничивает число элементов, **unbounded** может расти до исчерпания памяти. Ограниченная очередь с ожиданием создаёт обратное давление на производителя.
- При заполнении можно ждать, отклонять новую задачу или перезаписывать старую. Здесь выбираем ожидание без перезаписи.
- **FIFO** гарантирует порядок извлечения, но не порядок завершения обработки несколькими потребителями. Приоритетная очередь выбирает задачи по приоритету.
- Закрытие запрещает новые вставки, будит ожидающих и позволяет потребителям разобрать остаток.

## Примеры

### Два условия для одной очереди

Фрагменты относятся к одному классу `SyncedQueue<T>`. Конструктор задаёт положительную ёмкость; `0` отклоняется. Для простоты перемещение `T` и его деструктор предполагаются не бросающими исключений.

```cpp
// <queue>, <mutex>, <condition_variable>, <optional>, <utility>, <cstddef>
std::queue<T> q_;
std::mutex mutex_;
std::condition_variable not_empty_, not_full_;
std::size_t capacity_;
bool active_ = true;
```

### Добавление с ожиданием места

```cpp
bool Push(T value) {
    std::unique_lock lock(mutex_);
    not_full_.wait(lock, [&] {
        return !active_ || q_.size() < capacity_;
    });
    if (!active_) return false;
    try {
        q_.push(std::move(value));
    } catch (...) {
        lock.unlock();
        not_full_.notify_one(); // место осталось для другого производителя
        throw;
    }
    lock.unlock();
    not_empty_.notify_one();
    return true;
}
```

Статус сообщает об отказе при закрытии. Передача параметра по значению означает, что `false` не гарантирует сохранности исходного объекта, переданного через `std::move`.

### Извлечение и закрытие

```cpp
std::optional<T> Pop() {
    std::unique_lock lock(mutex_);
    not_empty_.wait(lock, [&] { return !active_ || !q_.empty(); });
    if (q_.empty()) return std::nullopt; // закрыта и разобрана
    T value = std::move(q_.front());
    q_.pop();
    lock.unlock();
    not_full_.notify_one();
    return std::optional<T>{std::move(value)};
}

void StopAcceptPushes() {
    {
        std::lock_guard lock(mutex_);
        active_ = false;
    }
    not_full_.notify_all();
    not_empty_.notify_all();
}
```

`Push` уведомляет потребителей через `not_empty_`, а `Pop` — производителей через `not_full_`. Закрытие будит обе стороны.

### Потребитель и завершение системы

```cpp
// Потребитель:
while (auto task = queue.Pop()) {
    Process(*task); // вне блокировки очереди
}

// Координатор: все производители и потребители уже запущены
for (auto& producer : producers) producer.Wait();
queue.StopAcceptPushes();
for (auto& consumer : consumers) consumer.Wait();
```

Сначала заканчивают все производители, затем закрывается очередь, затем потребители дорабатывают остаток. Отдельный `CanConsume()` для такого цикла не нужен.

### Ёмкость и результат ожидания

```cpp
// <stdexcept>; конструктор того же SyncedQueue<T>
explicit SyncedQueue(std::size_t capacity) : capacity_(capacity) {
    if (capacity_ == 0) throw std::invalid_argument("Zero capacity");
}
```

При добавлении `PopFor()` различай три исхода: элемент, таймаут и закрытая пустая очередь. Одного `optional<T>` для их различения недостаточно: нужен статус или вариант результата.

Закрытие и добавление упорядочены одним мьютексом: вставка до закрытия принята, попытка после него отклоняется. Повторное закрытие безопасно и не удаляет уже принятые элементы.

## Подводные камни

- Возврат ссылки на `front()` после снятия блокировки небезопасен: другой поток может удалить элемент. Возвращай извлечённое значение.
- `CanConsume()` и `empty()` — только снимки. У блокирующего `Pop()` пустой результат означает конец работы, а у `TryPop()` может означать лишь временную пустоту.
- Предикаты обоих ожиданий должны учитывать закрытие; одного изменения флага без уведомлений недостаточно.
- Ожидание производителя до запуска потребителей может зависнуть на полной очереди. Один производитель не должен закрывать очередь, пока остальные ещё работают.
- Закрытие не заменяет ожидание завершения потоков перед уничтожением очереди. Обычный `condition_variable::wait()` не прерывается автоматически stop-запросом `jthread`.
- Повторный последовательный `Wait()` можно поддержать проверкой `joinable()` перед `join()`. Это не разрешает конкурентные вызовы `Wait()` без синхронизации.
- Статистические счётчики производителей и потребителей можно читать и изменять атомарно с `relaxed`; итог проверяй после `join()`.
- `std::queue` поддерживает move-only элементы при подходящих операциях. `std::vector` также поддерживает многие move-only типы: выбор `deque` не является единственной причиной такой возможности.
- Лимит элементов не ограничивает все байты: задачи могут владеть большими объектами, а ожидающие производители уже держат параметры `Push`.
- Для бросающего перемещения нужна отдельная политика сохранности данных. Учебный пример выше ограничивает тип элемента.
- FIFO не гарантирует справедливость пробуждения потоков. Успешные повторные запуски не доказывают отсутствие гонок и дедлоков.

## Саммари

Ограниченная блокирующая очередь использует один мьютекс и два условия: «не пусто» и «не полно». Извлекай значение целиком, сообщай об отказе приёма и закрывай очередь с пробуждением обеих сторон и доработкой остатка.
