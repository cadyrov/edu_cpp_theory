# 8. Атомарные типы данных

## Суть

- Атомарные операции предотвращают гонку данных на самом атомарном объекте. Несколько операций подряд не становятся одной транзакцией; связанные обычные данные требуют корректного протокола синхронизации.
- `std::atomic_flag` — флаг с гарантированно lock-free операциями проверки и изменения. `std::atomic<T>` предоставляет более общий интерфейс, но может использовать внутренние блокировки.
- Для основного шаблона `atomic<T>` нужен тривиально копируемый тип, удовлетворяющий требованиям копирования и перемещения. Для некоторых типов есть отдельные специализации.
- `is_lock_free()` проверяет свойство объекта; `is_always_lock_free` (C++17) сообщает, гарантировано ли оно для данной специализации на целевой платформе.
- С C++20 `wait(old)` позволяет ждать изменения значения, а `notify_one()` / `notify_all()` уведомляют ожидающих. Само ожидание может блокироваться даже у `atomic_flag`.

## Примеры

### `atomic_flag` и `atomic<bool>`

```cpp
#include <atomic>

std::atomic_flag flag{}; // C++20: опущен; до C++20 — ATOMIC_FLAG_INIT
bool was_set = flag.test_and_set(); // поднять, вернуть прежнее состояние
bool is_set = flag.test();          // только прочитать, C++20
flag.clear();                      // опустить

std::atomic<bool> ready{false}; // также есть алиас std::atomic_bool
bool current = ready.load();
ready.store(true);
bool previous = ready.exchange(false); // заменить и вернуть старое значение
```

У `atomic_flag` нет `store(true)` или CAS; у `atomic<bool>` они есть. Ни один из этих объектов нельзя копировать как обычное значение — читай значение через соответствующую операцию.

### CAS: сравнить и заменить

```cpp
std::atomic<bool> busy{false};
bool expected = false;
bool acquired = busy.compare_exchange_strong(expected, true);
// Успех: busy стал true, expected не изменился.
// Неудача: busy не изменён, expected получил фактическое значение.
```

`compare_exchange_weak` может сообщить о неудаче даже при совпадении, поэтому обычно применяется в цикле. Для захвата именно свободного флага нужно каждый раз ожидать `false`:

```cpp
bool expected = false;
while (!busy.compare_exchange_weak(expected, true)) {
    expected = false;
}
// захватили; после работы нужно освободить через busy.store(false)
```

Без сброса `expected` после неудачи следующий вызов может успешно заменить `true` на `true`, хотя ресурс занят другим потоком. Это пример активного ожидания, а не готовый lock-free алгоритм.

### Одноразовая публикация данных с ожиданием

```cpp
#include <atomic>
#include <thread>

int main() {
    int data = 0;
    int result = 0;
    std::atomic<bool> ready{false};
    {
        std::jthread consumer([&] {
            ready.wait(false); // ждать, пока значение отличается от false
            result = data;
        });
        std::jthread producer([&] {
            data = 42;
            ready.store(true);
            ready.notify_one();
        });
    }
    // result == 42
}
```

Порядок памяти по умолчанию — `seq_cst`; здесь он обеспечивает публикацию `data` через флаг. Если производитель успел раньше потребителя, `wait(false)` увидит `true` и не станет ждать. Повторных записей в `data` после публикации в этом примере нет.

## Подводные камни

- Lock-free не означает «одна машинная инструкция», отсутствие ожидания в программе или гарантию завершения каждого потока за ограниченное число шагов.
- Атомики не устраняют ошибки времени жизни, дедлоки самодельных блокировок и гонки логики. `load()` с последующим `store()` не заменяет RMW.
- Для `wait(old, order)` подходят порядки чтения: `relaxed`, `consume`, `acquire`, `seq_cst`; `release` и `acq_rel` недопустимы. Порядок по умолчанию — `seq_cst`.
- `notify_*()` не меняет значение. Сначала измени состояние, затем уведомляй; без изменения `wait(old)` продолжит ожидание.
- В отличие от обычного `condition_variable::wait()`, атомарный `wait(old)` не возвращается только из-за ложного пробуждения: он повторно проверяет значение внутри.
- Краткое изменение A → B → A может остаться незамеченным ожидающим. Булевый флаг не хранит число событий; для этого нужен другой протокол, например счётчик поколений.
- Обычные данные публикует синхронизация через атомик, а не сам `notify`. Без изучения модели памяти не заменяй операции примера на `relaxed`.
- При построении мьютекса пробуждение не означает владения: после `wait(true)` нужно снова попытаться атомарно захватить флаг.
- Флаг остановки не разбудит поток, застрявший в `tasks.pop()`. Завершение блокирующей очереди должно иметь отдельный протокол закрытия и пробуждения.
- В обработчике сигнала нельзя выполнять произвольный код: для примера с SIGINT ограничься lock-free операцией над `atomic_flag`. Вывод, ожидание и работу с очередью оставь обычному потоку.

## Саммари

`atomic_flag` — простой lock-free флаг; `atomic<T>` даёт чтение, запись, обмен и CAS. `wait` ждёт изменения, `notify` будит ожидающих. Атомарность отдельных операций не заменяет продуманный протокол доступа и завершения.
