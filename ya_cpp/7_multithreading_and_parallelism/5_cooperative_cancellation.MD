# 5. Прерываемость потоков

## Суть

- **Кооперативная остановка**: внешний код просит завершиться, а поток проверяет запрос и выходит в безопасной точке. Принудительное убийство может оставить захваченные мьютексы и повреждённые данные.
- В C++20 `std::stop_source` отправляет запрос через `request_stop()`, `std::stop_token` проверяет его через `stop_requested()`, `std::stop_callback` регистрирует реакцию.
- Они связаны общим **stop state**. Запрос необратим; копии источника и токена используют то же состояние. Для нового цикла работы нужен новый источник.
- `std::jthread` передаёт свой токен первым аргументом, если вызываемый объект принимает его перед остальными аргументами. Деструктор связанного с потоком `jthread` вызывает `request_stop()`, затем `join()`.
- Отмена отдельной задачи не обязательно означает остановку обслуживающего её потока. Политику завершения выбирает приложение.

## Примеры

### Остановка вычислений

```cpp
#include <stop_token>
#include <thread>

void ProcessChunk() {
    // небольшой конечный этап работы
}

int main() {
    std::jthread worker([](std::stop_token token) {
        while (!token.stop_requested()) {
            ProcessChunk();
        }
    });

    // основная логика приложения
    worker.request_stop(); // только запрос, не ожидание завершения
    worker.join();         // здесь ждём фактического завершения
}
```

Источник запроса можно передать другому коду:

```cpp
auto source = worker.get_stop_source();
auto token = worker.get_stop_token();
source.request_stop(); // тот же запрос, что worker.request_stop()
```

### Прерываемое ожидание очереди

Фрагмент потребителя: `queue`, `mutex` и `cv` живут дольше потока; `cv` имеет тип `std::condition_variable_any`.

```cpp
std::jthread consumer([&](std::stop_token token) {
    while (true) {
        std::unique_lock lock(mutex);
        if (!cv.wait(lock, token, [&] { return !queue.empty(); })) {
            break; // запрошена остановка, очередь пуста
        }
        auto task = std::move(queue.front());
        queue.pop();
        lock.unlock();
        ProcessTask(task);
    }
});
```

`wait` возвращает результат предиката под мьютексом. Если запрос уже поступил, но очередь непуста, потребитель продолжает обработку.

Для приведённой очереди, где производитель не блокируется на заполнении, сначала прекрати поступление задач:

```cpp
producer.request_stop();
producer.join();          // новых задач больше не будет
consumer.request_stop();
consumer.join();          // дорабатывает очередь и выходит
```

Если остаток очереди не нужен, после `wait()` отдельно проверь `token.stop_requested()` и выйди до извлечения следующей задачи. Уже выполняющийся `ProcessTask()` сам по себе не прервётся.

### Реакция на запрос

```cpp
#include <atomic>
#include <stop_token>

// Фрагмент внутри функции:
std::atomic<bool> notified{false};
std::stop_source source;
std::stop_callback callback(source.get_token(), [&] {
    notified.store(true);
});
source.request_stop(); // синхронно выполняет зарегистрированный колбэк
```

Объект `callback` хранит регистрацию. Если запрос уже поступил, колбэк выполняется сразу при регистрации в регистрирующем потоке; иначе — в потоке, который успешно подал запрос.

### Остановка группы и блокирующих производителей

Если работники зависят друг от друга, сначала запроси остановку **у всех**, затем вызывай `join()` у каждого. Последовательное уничтожение `jthread` может ждать первый поток, пока второй ещё не получил запрос.

У bounded-очереди производитель может застрять внутри `Push()`: одного `request_stop()` недостаточно. Протокол закрытия должен будить его ожидание; нельзя сначала остановить всех потребителей, а затем ждать производителя с полной очередью.

## Подводные камни

- `request_stop()` не убивает поток и не прерывает обычный `sleep_for()`, блокирующий ввод-вывод или вычисление без проверок. Задержка остановки зависит от кода.
- Явный `join()` не запрашивает остановку. Бесконечный рабочий цикл без предварительного запроса может заставить его ждать вечно.
- Обычная `condition_variable` не реагирует на токен автоматически. Для стандартного сценария используй `condition_variable_any::wait(lock, token, predicate)`.
- Самодельная связка `stop_callback` и обычной `condition_variable` требует защиты от потери уведомления: одного `notify_one()` в колбэке недостаточно.
- Колбэки должны быть короткими и не бросать исключений: исключение из них вызывает `std::terminate`. Захват мьютекса в колбэке может привести к дедлоку, если вызывающий `request_stop()` уже владеет им.
- Деструктор `stop_callback` может ждать выполняющийся колбэк. Не уничтожай регистрацию под мьютексом, который нужен этому колбэку.
- У производителя и потребителя разные stop state. Обратный порядок уничтожения `jthread` не заменяет явный протокол завершения: потребитель может уйти раньше последней отправленной задачи.
- Метод называется `request_stop()`, не `stop_request()`. Сохранённый `stop_source` остаётся допустимым после завершения потока, но запрос уже не влияет на законченную работу.

## Саммари

Передавай `stop_token`, проверяй его в безопасных точках и используй прерываемое ожидание. Разделяй запрос и ожидание завершения, заранее выбирай политику для оставшихся задач и согласуй остановку связанных потоков.
